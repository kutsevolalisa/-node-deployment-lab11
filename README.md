# Deployment API Lab — практична робота №11

Стартовий Express API до роботи з розгортання серверних застосунків. Код маршрутів, читання конфігурації та тести реалізовано. За методичкою потрібно налаштувати команди запуску, змінні середовища, автоматичні перевірки й публікацію сервісу, а потім перевірити оновлення версії.

## Підготовка

Потрібні Node.js 24, npm, Git і GitHub CLI. Відкрийте каталог із package.json та виконайте:

```sh
npm ci
npm test
```

До першого запуску виконайте три завдання:

1. **P1:** замініть наявний блок scripts у package.json повним блоком із test, start і dev за кроком 2 методички. Команда `npm pkg get scripts` має показати всі три записи.
2. **P2:** доповніть .env.example та створіть його локальну копію .env.
3. **P3:** додайте кроки виконання до .github/workflows/ci.yml за повним прикладом із кроку 3. Коментар P3 не замінює робочої конфігурації GitHub Actions.

Перед публікацією зафіксуйте зміни конфігурації комітом і передайте їх на GitHub. Під час перевірки оновлення змініть номер версії у src/release.js з 1.0.0 на 1.1.0.

## Маршрути

- GET /health — 200: HTTP-процес відповідає.
- GET /ready — 200: застосунок готовий обробляти запити. Зовнішніх залежностей немає; в API з БД перевірку готовності потрібно доповнити перевіркою її доступності.
- GET /api/v1/info — 200: назва сервісу, режим бібліотек nodeEnv, середовище environment, повідомлення message, номер версії version та ідентифікатор коміту revision.
- Невідомий маршрут — 404 із кодом error.code: ROUTE_NOT_FOUND.

## Конфігурація та запуск

PORT задає порт процесу; за відсутності використовується 3000. NODE_ENV визначає режим роботи бібліотек, а APP_ENV позначає середовище застосунку: development, staging або production. APP_MESSAGE містить текст, який повертається у відкритій відповіді API; конфіденційні дані до нього не додають.

Номер version читається із src/release.js. Для revision спочатку використовується DEPLOY_REVISION, потім RENDER_GIT_COMMIT; якщо обидві змінні відсутні — local. За ручного розгортання виконайте `git rev-parse HEAD` і запишіть отриманий повний ідентифікатор коміту в DEPLOY_REVISION. Сам текст команди значенням цієї змінної бути не повинен.

Сервер приймає з’єднання на 0.0.0.0. Після доповнення scripts команда npm start запускає сервер зі змінними, уже переданими процесу. Вона не читає .env. Для локального запуску npm run dev додатково завантажує цей файл через --env-file=.env. На платформі змінні задаються в налаштуваннях сервісу.

## GitHub та вхід через CLI

Крок 3 методички містить реєстрацію на GitHub, створення порожнього публічного репозиторію через сайт і передавання локальних файлів. [Офіційна інструкція встановлення gh для macOS, Windows і Linux](https://github.com/cli/cli#installation).

```sh
gh auth login --git-protocol https --web --scopes workflow
gh auth setup-git --hostname github.com
gh auth status --hostname github.com
```

Підтвердьте доступ GitHub CLI в браузері та перевірте ім’я користувача у статусі входу. Дозвіл workflow потрібний для додавання файлів GitHub Actions. Параметри git config user.name і user.email визначають автора комітів; вони не замінюють автентифікацію та не створюють цифрового підпису.

## Перевірка запущеного API

Для локального сервера з NODE_ENV=production та APP_ENV=staging виконайте:

```sh
node scripts/check-api.mjs http://localhost:4100 1.0.0 staging
```

Для опублікованого сервісу вкажіть його адресу та середовище production. Після оновлення release.js використовуйте 1.1.0. За потреби четвертим аргументом можна передати очікуваний повний revision.

Сценарій надсилає чотири запити й перевіряє статуси, JSON, версію та середовище. За невідповідності очікуваному результату він завершується з ненульовим кодом. Граничний час очікування одного запиту — 120 секунд.

## Безкоштовне виконання

Сторінка реєстрації Render: https://dashboard.render.com/register. Для входу використайте власний GitHub. У кроці 4 методички описано workspace, Project і Web Service. Перед створенням сервісу перевірте Instance Type Free. Розгорніть Advanced settings / Advanced, щоб налаштувати додаткові поля, зокрема змінні середовища й Health Check Path.

Використовуйте безкоштовні або пробні версії ПЗ та безкоштовні тарифи, доступні без платіжних даних. Банківську картку й іншу платіжну інформацію не додавайте. Якщо під час реєстрації або вибору тарифу виникають сумніви, зверніться до викладача.

Основний варіант — Render Free та GitHub Actions у публічному репозиторії зі стандартним середовищем ubuntu-latest. За недоступності Render погодьте з викладачем резервний варіант: Codespaces у межах включеної квоти або локальний запуск. Тимчасовий доступ Codespaces не є постійним розміщенням робочого сервісу; локальний варіант не підтверджує хмарного розгортання.

.env і node_modules до Git не додають. Після збереження всіх матеріалів видаліть навчальне середовище Codespaces: навіть у зупиненому стані воно використовує квоту сховища.
